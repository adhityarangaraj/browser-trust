# BrowserTrust — `sol.md`
## Product vision, architecture, and phased implementation plan

This document is the source of truth for BrowserTrust's intended architecture, implementation phases, technical constraints, and acceptance criteria. Before making changes, every coding agent must read `sol.md`, `AGENTS.md`, `README.md`, and `PROGRESS.md`.

Keep these documents consistent with the actual code. Do not claim planned or unverified features are implemented.

## 1. Product vision

BrowserTrust is a standalone, general-purpose Chrome Manifest V3 extension that helps users understand observable website behavior: what happened, which browser/page API was called, where a request was directed, and why an observed sequence may deserve review.

The product should work across permitted ordinary websites, not just the local testbed. The testbed is a reproducible fixture, not a special case in product logic. BrowserTrust must not depend on Redact Agent, uBlock Origin, or another extension.

The long-term product combines browser/page activity observation, network destination visibility, event normalization and storage, event correlation, deterministic findings with supporting evidence, an evidence-based activity assessment, and optional AI contextual analysis in a later phase.

### Core truthfulness rule

BrowserTrust must distinguish:
1. **Observed:** directly supported by browser metadata or an observed API call.
2. **Inferred:** a plausible relationship based on a sequence of events.
3. **Unknown:** information that available browser APIs do not expose.

Never claim a particular value was transmitted unless reliable evidence establishes it. A form submission followed by a request is temporal correlation, not proof that the form values were sent. Never label a website definitively safe simply because no suspicious behavior was detected.

## 3. Architecture and responsibilities

Reuse the existing code. Do not recreate the project or add a second event pipeline.

- `src/shared/`: shared event types, message contracts, protocol definitions, URL utilities.
- `src/config/`: settings, monitoring controls, and site-access/permission handling.
- `src/content/`: isolated-world content scripts, page/DOM/form observers, hook-message relay.
- `src/page-hooks/`: MAIN-world wrappers for selected page APIs.
- `src/collectors/network.ts`: browser network-request metadata collection subject to Chrome permissions and API limits.
- `src/background/`: service worker, message routing, collector lifecycle.
- `src/core/`: event validation, normalization, ingestion pipeline, and bounded local storage.
- `src/analysis/`: deterministic rule engine, findings, evidence links, assessment logic.
- `src/popup/`: extension UI and views.
- `public/manifest.json`: Manifest V3 configuration.
- `scripts/build.mjs`: build and static asset copying.
- `testbed/`: local synthetic website and collector used only for controlled testing.
- `tests/`: unit and integration tests.

Use the repository's actual structure if it differs; update this document only when an intentional architecture change is made.

All event sources must use the common ingestion pipeline. Treat content-script and MAIN-world messages as untrusted. Validate and normalize input, derive sender/source details from trusted browser context when possible, strip URL query strings and fragments where appropriate, and never store raw passwords, authentication tokens, cookie values, clipboard contents, full storage values, or sensitive form values.

## 4. General-purpose monitoring and limitations

The extension should operate on websites for which the user has granted the necessary permissions. Do not hardcode the testbed hostname into product logic.

Document and respect these limits:
- Optional host permissions limit coverage to permitted sites.
- Chrome restricts access to browser-internal pages, some special schemes, and other contexts.
- `chrome.webRequest` visibility depends on browser APIs and granted permissions; the current design collects request metadata, not request/response bodies.
- MAIN-world wrappers observe selected calls through wrapped entry points. A page may bypass or tamper with wrappers or use another execution context.
- Storage method wrappers may not observe every access pattern, such as direct property access.
- API calls involving geolocation, clipboard, or media capture are not proof of successful access or completed transmission.
- Chrome extensions generally cannot comprehensively inspect the internal behavior of arbitrary other extensions.
- Events from different collectors may describe the same underlying action. Deduplicate only when there is reliable evidence for doing so.
- Never imply complete protection or universal visibility.

Keep collection local by default. Do not add remote telemetry, cloud services, or external AI calls without a separately scoped future phase.

## 6. Phase 3 — Behavioral analysis, destinations, and UI

### Objective

Turn BrowserTrust from an event viewer into a useful, evidence-based behavioral analysis tool. AI/LLM integration is out of scope for Phase 3.

### 6.1 Integrate the existing analysis engine

Inspect `src/analysis/` and connect the existing engine to the live event pipeline. Do not build a parallel pipeline.

Implement a small, explainable set of deterministic rules where the collected evidence supports them:

1. **Form submission followed by network activity:** identify a sequence within a configurable time window as worth reviewing. Do not claim form values were transmitted unless the payload is reliably verified.
2. **Sensitive API activity followed by a request:** show a relationship only when evidence supports it; otherwise describe it as temporal correlation.
3. **Unexpected or repeated external communication:** use explainable configurable conditions. Do not label ordinary external requests malicious merely because they exist.
4. **Sensitive capability requests:** highlight supported API calls involving capabilities such as geolocation, clipboard, or media capture. Do not claim successful access unless known.

Keep the rule set small, testable, and explainable. Avoid arbitrary scores and noisy alerts.

### 6.2 Finding model and lifecycle

Each finding should contain a stable finding ID, rule ID and title, severity/category, explanation, supporting event IDs and timestamps, source website and destination when available, evidence-strength classification, and known uncertainties.

Evaluate relevant events through the common pipeline. Prevent duplicate findings for the same event sequence, persist findings locally where appropriate, keep storage bounded, and handle service-worker restarts. Analysis must not block ingestion or freeze the popup.

### 6.3 Destination tracking

Show observed network destinations with hostname, request method where available, timestamp, initiating page/source context where available, observation source (browser network metadata or page hook), status only when available, and related events/findings.

Group by hostname where useful. Deduplicate repeated observations only when there is sufficient evidence they represent the same request.

Do not inspect or store sensitive request bodies to make the demo more compelling. If a POST is observed but its payload is not available, say that the payload was not verified.

### 6.4 Evidence-based assessment

Provide understandable states for the current site's observed activity:
- **No suspicious activity observed:** monitoring is active, relevant observations exist, and no rules currently match.
- **Review recommended:** behavior deserves review but evidence is ambiguous or incomplete.
- **Suspicious activity detected:** a supported rule triggered with meaningful evidence.
- **Insufficient evidence:** monitoring is off, permissions are missing, observations are incomplete, or too little activity has been observed.

These states describe available evidence, not a definitive verdict on whether a website is safe or malicious. Show monitoring status and coverage limitations. Prefer explicit reasons over arbitrary numerical risk scores.

### 6.5 UI redesign

Create a polished, compact Chrome extension security dashboard using the existing lightweight stack unless there is a strong reason to change it.

Theme:
- Red `#E53945`: suspicious findings, critical alerts, high-attention actions.
- Black `#151515`: primary dark surfaces and headings.
- White `#FFFFFF`: main content surfaces and readable text.
- Green `#238636`: reassuring operational states and verified normal states.
- Orange `#F59E0B`: warnings and uncertain/review-needed states, used sparingly.
- Neutral gray `#6B7280`: secondary text and metadata.

Use the colors with restraint and maintain accessible contrast.

Include:
- Product header and monitoring status.
- Current hostname and permission/coverage status.
- Evidence-based assessment.
- Summary counts for observed events, network requests, and findings.
- Recent activity timeline.
- Expandable finding details with supporting evidence.
- Destination overview and links to related events.
- Useful empty, loading, error, disabled-monitoring, and permission-denied states.

Use actual implementation data only. No fake charts, seeded security events, fabricated alerts, or decorative risk scores. Keep the popup readable and uncluttered; use tabs or a separate extension page if needed.

### 6.6 Phase 3 tests

Add tests for rule matches and non-matches, correlation time-window boundaries, duplicate-finding prevention, severity and assessment states, supporting event references, missing optional metadata, destination normalization/grouping, monitoring-disabled and permission-limited conditions, and bounded persistence where applicable.

Run typecheck, tests, and production build. Do not claim Chrome behavior has been verified without a real-browser test.

### Phase 3 acceptance criteria

- Existing collectors continue to use the common pipeline.
- New events trigger relevant deterministic rules.
- Findings include supporting event IDs and honest explanations.
- Destination metadata is visible and attributed to its observation source.
- Assessment states distinguish no findings from insufficient evidence.
- The redesigned UI uses real data and handles empty/error/permission states.
- Tests cover rules and assessment logic.
- README, AGENTS, and PROGRESS match actual functionality and verified results.
- No AI, remote service, database, or unrelated architecture rewrite is introduced.

## 7. Phase 3 must be demo-ready

Phase 3 is not complete merely because the analysis engine and UI compile. By the end of Phase 3, BrowserTrust must be ready for a simple, repeatable three-minute demonstration without AI.

The demo-ready Phase 3 deliverable must support this complete flow:
1. Build and load the extension in Chrome.
2. Open the local synthetic testbed.
3. Trigger a form submission, a storage operation, and a POST request to the local collector.
4. See the actual events appear in BrowserTrust.
5. See the destination hostname and available request metadata.
6. See a deterministic rule produce a finding from the observed event sequence.
7. Open the finding and inspect its supporting events, explanation, and uncertainty.
8. See an evidence-based assessment that does not falsely claim the site is proven safe or malicious.
9. Reset the testbed and repeat the scenario reliably.

Before declaring Phase 3 complete:
- Run the typecheck, automated tests, and production build.
- Manually verify the entire flow in Chrome using the local testbed.
- Verify that monitoring disabled, missing permissions, and empty activity produce honest UI states.
- Test at least one permitted ordinary website to confirm the extension is not hardcoded to the testbed.
- Fix demo-blocking bugs and update the README with exact setup and demo instructions.
- Clearly document any behavior that could not be verified.

Do not add new features at the expense of making this end-to-end scenario reliable. A small, polished, working demo is more valuable than a broad but unreliable feature set.

## 8. Later phases — not required for the Phase 3 demo

### Phase 4 — Correlation quality and coverage improvements
Improve deduplication, event lineage, permission coverage messaging, browser limitation handling, and detection precision. Add rules only when evidence and tests justify them.

### Phase 5 — Optional AI contextual analysis
AI is not required for the R3 demo and must not delay Phase 3. Consider it only if it demonstrably improves explanations beyond deterministic rules. If added later, make it opt-in, send only minimized/normalized event data, disclose what leaves the device, and never send raw sensitive values by default. Keep deterministic checks functional without AI.

### Phase 6 — Demo hardening and presentation
Once the Phase 3 acceptance criteria are met, rehearse the scenario, confirm reproducibility, document limitations, and polish the presentation. Do not overstate detection or coverage.

## 10. Definition of a successful Phase 3 demo

Using the local testbed, a user should be able to:
1. Trigger synthetic form activity.
2. Observe the form event in BrowserTrust.
3. Observe the outgoing request and its destination.
4. See a deterministic finding connecting relevant events, with appropriate uncertainty.
5. Open the finding and inspect supporting evidence.
6. Understand the current assessment and its limitations.

The extension should also remain usable on permitted ordinary websites, without special-case testbed logic.

**BrowserTrust explains observable browser behavior, shows where requests go, and presents evidence-backed reasons to review suspicious activity. It does not claim to prove that a website is universally safe or malicious.**
