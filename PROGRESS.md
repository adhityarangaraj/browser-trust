# Progress

## Dashboard foundation and Sites & Activity integration (Phases 1 and 2)

- Added a separate React dashboard extension page with responsive sidebar navigation and views for Overview, Sites & Activity, Permissions, Web Recall, Follow-up Tracker, Context Keeper, and Trust Monitor. Screen time is consolidated into Sites & Activity; no separate Screen time destination remains.
- Refined the light SaaS interface around a centralized crimson/neutral/semantic palette, locally bundled Inter, Lucide outline icons, compact navigation, readable data table, responsive layouts, focus states, and reduced-motion support.
- Sites & Activity uses opt-in Chrome History data, local calendar ranges, hostname grouping, visit/latest-visit sorting, and daily visit counts. It also offers separate opt-in active browsing-time tracking, estimated only for an active HTTP(S) tab in the focused window while Chrome reports the user active; hostname/day records are bounded to 30 days and locally stored.
- Added only optional `history`, `tabs`, `idle`, and `alarms` permissions. Permission prompts are user initiated. No backend or history transmission was added; existing popup, activity page, collectors, event pipeline, and monitoring behavior are unchanged.
- Dashboard styles use a centralized theme imported through its TSX entry; `verify-dist` checks generated dashboard CSS and JS.
- The dashboard can be opened directly at `chrome-extension://<installed-extension-id>/dashboard.html` after loading `dist/`. Manual Chrome verification is pending.
- Phase 2 validation has not been run at the user request. Run `npm run check` before release. Manual Chrome verification remains needed for permission prompts, history ranges, tracking transitions, retention/clear behavior, worker/browser lifecycle, and direct extension URL access.

## Phase 3 implementation checkpoint

Implemented in the existing Phase 2 architecture:

- Connected deterministic analysis to the shared event pipeline and added bounded, locally persisted findings with stable IDs and duplicate prevention.
- Added explainable findings for trusted form activity followed by browser-observed requests, selected sensitive API calls, capability-call/request temporal relationships, and repeated cross-origin POST observations.
- Findings include supporting event IDs and timestamps, source/destination where available, evidence strength, and explicit limitations. Request bodies and sensitive field values are not collected.
- Added grouped destination summaries that retain observation counts and label browser metadata versus page-hook evidence.
- Reworked the popup around monitoring and permission coverage, evidence-based assessment states, event/network/finding counts, expandable evidence, destinations, and recent activity.
- Redesigned the popup as a dark, assessment-first summary with observed-behavior labels and compact previews; added a View Activity extension page using the same stored events and findings.
- Kept the product general-purpose; the loopback testbed remains separate from extension source code.
- Updated README and agent guidance. `AGENTS.md` explicitly requires reading `sol.md` before planning or implementation.

- Phase 2 (rule correctness) completed on 2026-10-22: `BrowserTrustEvent` now carries an optional monotonic `sequence` number assigned by `EventPipeline`, and `analyze`/`analyzeEvent` sort by `(timestamp, sequence)` so events ingested in the same millisecond keep a deterministic chronological order. Validator accepts the field for backward compatibility with events stored before the counter existed. Added a dedicated test covering the tiebreaker. 90 Vitest tests + 9 Node tests + typecheck + build pass.
- Phase 3 (reachable Suspicious state) completed on 2026-10-22: `capabilityNetworkRule` now escalates to `high` severity when the following request is a cross-origin POST, with an updated title/explanation that still labels evidence as temporal-association. `repeatedExternalPostRule` emits an additional `high`-severity finding (distinct event anchor and ID) when the pattern sustains to six observations inside the same minute. Both findings coexist with the base medium ones. The assessment table's `suspicious-activity-detected` path is therefore reachable by real rules; README and `assessSite` tests updated. 92 Vitest tests + 9 Node tests + typecheck + build pass.
- Phase 4 (analysis & pipeline hardening) completed on 2026-10-22: three correctness/perf fixes. (1) `EventStore` now carries a `generation` counter that is bumped on every `clear()`; the analysis service captures the generation when a listener fires and silently drops its findings write if the store was cleared in the meantime, which closes the clear-events ↔ in-flight-analysis race that previously resurrected zombie findings. (2) `EventPipeline.emit` no longer awaits listener completion; a slow subscriber (such as the analysis queue) cannot back-pressure ingestion. `connectAnalysis` returns an `AnalysisConnection` with an `unsubscribe` and a `drain()` that tests and the background `clear-events` handler now call explicitly. (3) The analysis service clips history passed to rules to `MAX_RULE_WINDOW_MS` (60s), capping the per-event scan cost even when the 1000-event ring is full. Three new tests cover the clear-race, the window cap, and the drain-after-emit flow. 94 Vitest tests + 9 Node tests + typecheck + build pass.
- Phase 5 (webRequest enrichment + registrable-domain) completed on 2026-10-22: the `webRequest` collector now also subscribes to `chrome.webRequest.onCompleted` and `onErrorOccurred` and emits `request.completed` / `request.failed` events, each carrying the originating `requestId` on the common evidence shape. `summarizeDestinations` merges by `requestId` and now surfaces observed status codes, failure counts, and whether any observation to the host was cross-site, without ever double-counting `request.sent`. A new lightweight `src/shared/psl.ts` provides a documented registrable-domain heuristic with a small multi-label suffix list; `toDestination` populates the previously-unused `isThirdParty` flag using it. The popup destination preview surfaces `status`, `failed`, and `third-party`. Two new test files (`tests/psl.test.ts`) and expanded coverage in `tests/network.test.ts` + `tests/destinations.test.ts` lock in the new behaviour. 104 Vitest tests + 9 Node tests + typecheck + build pass.
- Phase 6 (new detection rules) completed on 2026-10-22: three new deterministic rules added to the standard set and registered through the common engine. (1) `hiddenCrossOriginIframeRule` (medium): a newly added iframe with `tag=iframe` + `hiddenHint=true` + cross-origin destination. (2) `dynamicThirdPartyScriptRule` (low): a `<script>` added after the initial page scan whose destination is on a different registrable domain (uses the Phase 5 PSL flag). (3) `scriptedFormNetworkRule` (low): a `form.submit_called` main-world-hook event followed within 30s by a browser-observed request in the same tab/origin — complements the existing trusted-submit rule without changing its strict host/method precision. README rule table updated; `tests/rules.test.ts` grew three dedicated tests covering match, non-match, and interaction with the strict `formNetworkRule`. 107 Vitest tests + 9 Node tests + typecheck + build pass.
- Phase 7 (popup UX) completed on 2026-10-22: the activity page now has a filter bar directly above the timeline — a case-insensitive text search over event label, action, source origin, destination host, collector and mechanism, plus a row of category chips (page / dom / form / storage / network / capability) with `aria-pressed` state that toggle timeline rows client-side without re-fetching stored events. Clicking any supporting-event link in a finding or destination row delegates through a single `document` click handler that preventDefaults the anchor, smooth-scrolls the row into view, and applies a short `bt-flash` animation (orange highlight fading over 1.4 s) so the connection is visible even when the row was already on screen. The popup itself is unchanged (deliberately — it stays compact). README updated. 107 Vitest tests + 9 Node tests + typecheck + build pass; the filter/flash behaviour is DOM wiring with no additional unit coverage.
- Phase 8 (export & share) completed on 2026-10-22: new `src/analysis/report.ts` exposes a pure `buildReport(events, findings, destinations, assessment, context, generatedAt)` plus `reportToJson` and `reportToMarkdown` builders. The Markdown report carries assessment headline + explanation, every finding with rule id / evidence strength / supporting event ids and timestamps / limitations, every destination row (methods, status codes, failure counts, third-party flag) and the event timeline, closing with a privacy footer stating that metadata only is collected. Popup footer gets a new **Copy report** button (writes Markdown to `navigator.clipboard`); the activity page footer additionally gets **Download JSON** which creates a blob URL, clicks a hidden anchor named `browsertrust-<host>-<timestamp>.json`, and revokes the URL. Both buttons disable when there is nothing to report. 111 Vitest tests + 9 Node tests + typecheck + build pass.
